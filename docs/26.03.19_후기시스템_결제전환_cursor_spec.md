## 2. DB 스키마

### 2.1 proof_assets 테이블 확장 (ALTER)

> 기존 `proof_assets` 테이블에 후기 전용 컬럼을 추가합니다.
> 기존 `type = "review"` 레코드와 호환됩니다.

```sql
-- 기존 proof_assets 테이블에 컬럼 추가 (실전 운영 기준)
ALTER TABLE public.proof_assets
  ADD COLUMN IF NOT EXISTS headline           TEXT,           -- 1단계: 짧은 헤드라인
  ADD COLUMN IF NOT EXISTS start_score        INTEGER,        -- 시작 점수
  ADD COLUMN IF NOT EXISTS current_score      INTEGER,        -- 현재/도달 점수
  ADD COLUMN IF NOT EXISTS target_score       INTEGER,        -- 목표 점수
  ADD COLUMN IF NOT EXISTS usage_days         INTEGER,        -- 사용 기간 (일)
  ADD COLUMN IF NOT EXISTS best_feature       TEXT,           -- 가장 도움된 기능 (전략 분석/약점 코칭 등)
  ADD COLUMN IF NOT EXISTS main_weakness_tag  TEXT,           -- 주요 약점 태그 (문장구조/Part7/문법 등)
  ADD COLUMN IF NOT EXISTS review_stage       INTEGER DEFAULT 1,  -- 1: 헤드라인만 | 2: 전체 후기
  ADD COLUMN IF NOT EXISTS reward_granted     BOOLEAN DEFAULT FALSE,  -- 보상 지급 여부
  ADD COLUMN IF NOT EXISTS reward_type        TEXT,           -- '3days' | '5days'
  ADD COLUMN IF NOT EXISTS consent_public     BOOLEAN DEFAULT FALSE,  -- 공개 노출 동의 여부
  ADD COLUMN IF NOT EXISTS is_featured        BOOLEAN DEFAULT FALSE,  -- 운영자 큐레이션 여부
  ADD COLUMN IF NOT EXISTS approved_at        TIMESTAMPTZ;    -- 운영자 승인 시각 (NULL = 미승인)

-- 공개 노출 조건: is_public = TRUE는 운영자 승인(approved_at IS NOT NULL) 후에만 TRUE로 변경
-- consent_public: 유저가 공개 동의한 경우 TRUE

-- RLS: 본인 데이터만 INSERT/UPDATE, 공개된 것은 모두 SELECT
ALTER TABLE public.proof_assets ENABLE ROW LEVEL SECURITY;

CREATE POLICY IF NOT EXISTS "proof_assets_own_write" ON public.proof_assets
  FOR ALL USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY IF NOT EXISTS "proof_assets_public_read" ON public.proof_assets
  FOR SELECT USING (is_public = TRUE OR auth.uid() = user_id);
```

### 2.2 공개 노출 흐름 (중요)

```
유저 후기 작성 (consent_public = TRUE)
    ↓
저장: is_public = FALSE, approved_at = NULL
    ↓
관리자 대시보드에서 검토
    ↓
승인 시: approved_at = NOW(), is_public = TRUE
미승인: 그대로 유지 (공개 안 됨)
    ↓
is_public = TRUE인 후기만 결제 페이지/랜딩에 노출
```

> ⚠️ **운영자 주의**: `consent_public = FALSE`인 후기는 절대 `is_public = TRUE`로 변경하면 안 됩니다.
> 승인 기준: 욕설/이상 문구 없음 + 최소 10자 이상 + 개인정보 미포함

## 3. 후기 수집 트리거 조건

> 아래 조건 중 **하나 이상** 충족 시 후기 요청 팝업을 노출합니다.
> (이미 후기를 제출한 유저에게는 노출하지 않습니다.)

### 3.1 트리거 조건 목록

| 조건 | SQL/로직 |
|------|----------|
| 최초 결제 후 5~7일 경과 | `CURRENT_DATE - subscriptions.created_at BETWEEN 5 AND 7` |
| 오답 10개 이상 등록 | `SELECT COUNT(*) FROM wrong_answers WHERE user_id = $1 >= 10` |
| 전략 분석 2회 이상 실행 | `SELECT COUNT(*) FROM strategy_cache WHERE user_id = $1 >= 2` |
| 오늘 할 일 3개를 3일 이상 확인 | `coaching_logs` 기준 날짜별 집계 3일+ |
| 시험 D-14 진입 | `users.exam_date - CURRENT_DATE <= 14` |

### 3.2 이미 후기 제출 여부 확인

```typescript
// 후기 요청 팝업 노출 전 확인
const { data: existing } = await supabase
  .from('proof_assets')
  .select('id, review_stage')
  .eq('user_id', userId)
  .eq('type', 'review')
  .maybeSingle();

// existing이 null이면 미제출 → 팝업 노출
// existing.review_stage === 1이면 1단계만 완료 → 2단계 유도 가능
// existing.review_stage === 2이면 완료 → 팝업 비노출
```

### 3.3 트리거 체크 훅 (클라이언트)

```typescript
// hooks/useReviewTrigger.ts
export function useReviewTrigger() {
  const [shouldShowReview, setShouldShowReview] = useState(false);

  useEffect(() => {
    async function checkTrigger() {
      const { data } = await supabase.rpc('check_review_trigger');
      // RPC: 위 조건들을 서버에서 체크하여 boolean 반환
      if (data?.should_show) setShouldShowReview(true);
    }
    checkTrigger();
  }, []);

  return { shouldShowReview };
}
```

```sql
-- Supabase RPC 함수
CREATE OR REPLACE FUNCTION check_review_trigger()
RETURNS JSONB
LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_user_id UUID := auth.uid();
  v_wrong_count INTEGER;
  v_strategy_count INTEGER;
  v_days_since_payment INTEGER;
  v_already_reviewed BOOLEAN;
BEGIN
  -- 이미 후기 제출 여부
  SELECT EXISTS(
    SELECT 1 FROM proof_assets
    WHERE user_id = v_user_id AND type = 'review'
  ) INTO v_already_reviewed;

  IF v_already_reviewed THEN
    RETURN '{"should_show": false}'::JSONB;
  END IF;

  -- 오답 수
  SELECT COUNT(*) INTO v_wrong_count
  FROM wrong_answers WHERE user_id = v_user_id;

  -- 전략 분석 수
  SELECT COUNT(*) INTO v_strategy_count
  FROM strategy_cache WHERE user_id = v_user_id;

  -- 결제 후 경과일
  SELECT EXTRACT(DAY FROM NOW() - MIN(created_at))::INTEGER
  INTO v_days_since_payment
  FROM subscriptions WHERE user_id = v_user_id AND paid = TRUE;

  -- 조건 체크
  IF (v_wrong_count >= 10)
     OR (v_strategy_count >= 2)
     OR (v_days_since_payment BETWEEN 5 AND 7)
  THEN
    RETURN '{"should_show": true}'::JSONB;
  END IF;

  RETURN '{"should_show": false}'::JSONB;
END;
$$;
```

## 5. 보상 로직

### 5.1 보상 기준

| 단계 | 조건 | 보상 | 횟수 제한 |
|------|------|------|----------|
| **1단계** | 헤드라인 제출 완료 (공개 동의 불필요) | `expires_at + 3일` | **1회 한정** |
| **2단계** | 전체 후기 작성 + 공개 동의 완료 | `expires_at + 5일 추가` | **1회 한정** |
| 중복 시 | 같은 단계 재제출 | 보상 없음 | — |

> **보상 정책 원칙**
> - 보상 기준은 "제출 완료" 여부만. 후기 품질 판단 없음.
> - 1단계는 공개 동의 없이도 보상 지급.
> - 2단계는 `consent_public = TRUE`인 경우에만 보상 지급.
> - 같은 사용자가 여러 번 제출해도 추가 보상 없음. `review_rewards` 테이블로 엄격히 제한.

### 5.2 보상 처리 함수 (Supabase RPC)

```sql
CREATE OR REPLACE FUNCTION grant_review_reward(
  p_asset_id UUID,
  p_stage INTEGER    -- 1 또는 2 (review_stage와 동일)
)
RETURNS JSONB
LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_user_id UUID := auth.uid();
  v_days INTEGER;
  v_reward_type TEXT;
  v_already_rewarded BOOLEAN;
  v_new_expires TIMESTAMPTZ;
  v_consent BOOLEAN;
BEGIN
  -- 2단계 보상은 consent_public 확인 필수
  IF p_stage = 2 THEN
    SELECT consent_public INTO v_consent
    FROM proof_assets WHERE id = p_asset_id AND user_id = v_user_id;

    IF NOT COALESCE(v_consent, FALSE) THEN
      RETURN '{"success": false, "reason": "consent_required_for_stage2"}'::JSONB;
    END IF;
  END IF;

  -- 중복 보상 방지 (동일 stage는 1회만)
  SELECT EXISTS(
    SELECT 1 FROM review_rewards
    WHERE user_id = v_user_id AND reward_step = p_stage
  ) INTO v_already_rewarded;

  IF v_already_rewarded THEN
    RETURN '{"success": false, "reason": "already_rewarded"}'::JSONB;
  END IF;

  -- 단계별 연장 일수 및 reward_type
  v_days := CASE p_stage WHEN 1 THEN 3 WHEN 2 THEN 5 ELSE 0 END;
  v_reward_type := CASE p_stage WHEN 1 THEN '3days' WHEN 2 THEN '5days' ELSE NULL END;

  -- subscriptions 연장 (이미 만료된 경우 NOW() 기준으로 연장)
  UPDATE subscriptions
  SET expires_at = GREATEST(expires_at, NOW()) + (v_days || ' days')::INTERVAL
  WHERE user_id = v_user_id AND paid = TRUE
  RETURNING expires_at INTO v_new_expires;

  -- 보상 로그 기록
  INSERT INTO review_rewards (user_id, asset_id, reward_step, days_added)
  VALUES (v_user_id, p_asset_id, p_stage, v_days);

  -- proof_assets 보상 완료 표시
  UPDATE proof_assets
  SET reward_granted = TRUE, reward_type = v_reward_type
  WHERE id = p_asset_id;

  RETURN jsonb_build_object(
    'success', TRUE,
    'days_added', v_days,
    'reward_type', v_reward_type,
    'new_expires_at', v_new_expires
  );
END;
$$;
```

### 5.3 클라이언트 보상 처리

```typescript
// 제출 완료 후 처리
async function handleReviewSubmit(step: 1 | 2, assetId: string) {
  const { data } = await supabase.rpc('grant_review_reward', {
    p_asset_id: assetId,
    p_step: step,
  });

  if (data?.success) {
    // 보상 완료 토스트 노출
    toast.success(`이용 기간이 ${data.days_added}일 연장되었습니다!`);
  }
}
```

## 주요 주의사항

1. **PDF 기능 없음**: 보상에 PDF 리포트 포함 금지. 보상은 **"기간 연장"만**.

2. **보상 중복 방지 (엄격 적용)**:
   - `review_rewards` 테이블에서 `(user_id, reward_step)` 조합으로 중복 체크
   - 1단계 보상: 1회 한정 (재제출해도 추가 지급 없음)
   - 2단계 보상: 1회 한정 (재제출해도 추가 지급 없음)
   - 보상 조건은 "제출 완료" 여부만. 후기 품질 평가 없음.

3. **공개 동의 정책**:
   - 1단계(헤드라인): `consent_public` 불필요. 보상 지급 가능.
   - 2단계(전체 후기): `consent_public = TRUE`인 경우에만 보상 지급.
   - `consent_public = FALSE` 후기는 절대 `is_public = TRUE`로 변경 금지.

4. **운영자 승인 필수**: 후기 작성 즉시 공개 노출 금지.
   - 작성 직후: `is_public = FALSE`, `approved_at = NULL`
   - 관리자 검토 후 승인 시에만: `approved_at = NOW()`, `is_public = TRUE`
   - 승인 기준: 욕설 없음 + 최소 10자 이상 + 개인정보 미포함

5. **모바일 퍼스트**: 모든 후기 UI는 모바일 기준으로 먼저 설계. 카드 너비 화면 width - 32px 패딩.

6. **기존 proof_assets 호환**: `type = 'review'`가 아닌 기존 레코드(before_after, insight)에는 새 컬럼이 NULL이므로 렌더링 시 null 처리 필수.

7. **`is_featured` 활용**: 관리자가 특별히 강조하고 싶은 후기에만 `is_featured = TRUE`. 결제 페이지 상단 카드는 `is_featured = TRUE` 우선 정렬.
