## 1. 프로젝트 개요

### 1.1 서비스 정의

토답(TODAP)은 토익 오답 노트 기반 AI 코칭 서비스입니다.
단순 오답 기록이 아닌, 결제 즉시 "지금 상황에 맞는 행동"을 제시하는 목표 달성형 학습 도구입니다.

> 🎯 **핵심 포지셔닝 메시지**
> "이번 시험 전 점수 올리고 싶은 사람만"
> → 기능 설명 ❌  "지금 상황 해결" ⭕

### 1.2 기술 스택

| 레이어 | 기술 | 비고 |
|--------|------|------|
| Frontend | Next.js (App Router) | Vercel 배포 |
| Backend / DB | Supabase (PostgreSQL) | RLS 적용 |
| Auth | Supabase Auth | 이메일 + OAuth |
| AI | OpenAI API | 코칭 엔진 |
| Payment | 토스페이먼츠 | 웹훅 연동 |
| 배포 | Vercel | toiknote.vercel.app |

## 2. 수익화 상품 구조

### 2.1 플랜 라인업

> 💡 **상품 설계 원칙**
> 기간 ❌ → 상황 ⭕
> 유저는 "30일짜리"를 사는 게 아니라 **"지금 이 상황을 해결"** 하는 것을 산다.

| 플랜명 | 기간 | 가격 | 포지셔닝 메시지 |
|--------|------|------|----------------|
| **파이널 압축** | 15일 | 29,900원 | 시험 2주 전 응급 전략 |
| **표준 코칭** | 30일 | 49,900원 | 기본 루틴 + 전략 |
| **정체 탈출** | 60일 | 79,900원 | 장기 교정 |

### 2.2 베타 단계 전략

> ✅ **베타 운영 방침**
> 베타 단계에서는 **15일 파이널 압축 플랜 단일 포지셔닝**을 권장합니다.
> 30일/60일 플랜은 업셀 또는 2차 단계로 분리하여 선택 피로를 제거합니다.

### 2.3 결제 후 즉시 제공 (온보딩 UX)

결제 완료 즉시 다음 세 가지를 화면에 노출합니다. 이 단계가 **"첫날 활성화"** 의 핵심입니다.

| # | 항목 | 구현 방법 |
|---|------|----------|
| ① | **약점 TOP3** | 오답 데이터 기반 AI 자동 추출 (OpenAI API) |
| ② | **오늘 할 일 3개** | 우선순위 코칭 리스트 (AI 생성) |
| ③ | **버려야 할 것 1개** | 지금 당장 손놓을 항목 (AI 생성) |

### 2.4 수익 구조 방향

| ❌ 기존 모델 (구독) | ⭕ 목표 달성형 모델 |
|-------------------|-------------------|
| MRR 중심 | 신규 유입 + 후기 중심 |
| Retention KPI | Activation + Outcome + Proof KPI |
| 반복 결제 유도 | 목표 달성 → 후기 → 신규 전환 루프 |

## 3. KPI 개발 명세

### 3.1 핵심 전환

```
구독 KPI ❌  →  목표 달성형 KPI ⭕
Retention ❌  →  Activation + Outcome + Proof ⭕
```

### 3.2 핵심 KPI 5가지

| # | KPI | 정의 | 측정 방법 |
|---|-----|------|----------|
| 1 | **고의도 유입** | 시험 D-14~D-30 구간 유저 비율 | 가입 시 시험일 입력 필드 수집 |
| 2 | **첫날 활성화율** | 결제 후 24시간 내 온보딩 3단계 완료율 | `activated_at` 컬럼 기록 |
| 3 | **7일 사용률** | 7일 내 코칭 3회 이상 진입 비율 | `coaching_logs` 집계 |
| 4 | **목표 달성 체감** | self-report 기반 (베타 피드백 폼) | Form 응답 수집 |
| 5 | **후기/추천 발생률** | `proof_assets` 생성 수 / 결제 수 | `proof_assets` 테이블 집계 |

### 3.3 활성화 정의 (24시간 기준)

결제 후 24시간 내 아래 세 가지를 **모두** 완료한 경우 `activated` 처리합니다.

```
활성화 조건 (AND 조건, 모두 충족해야 함)

  ① 약점 TOP3 확인 완료
  ② 오늘 할 일 3개 확인 완료
  ③ 오답 1개 이상 등록

→ users 테이블 activated_at 컬럼에 타임스탬프 기록
```

> ⚠️ **개발 주의사항**
> 유저가 자발적으로 돌아오길 기다리면 활성화율이 낮게 나옵니다.
> 결제 완료 즉시 자동 알림 시퀀스(이메일 or 인앱 메시지)가 함께 실행되어야 합니다.

### 3.4 7일 사용률 기준

```sql
SELECT user_id
FROM coaching_logs
WHERE created_at >= (결제일)
  AND created_at < (결제일 + INTERVAL '7 days')
GROUP BY user_id
HAVING COUNT(*) >= 3
```

### 3.5 후기 발생률 산식

```sql
-- 후기 발생률 = proof_assets 생성 수 / 결제 수
SELECT
  COUNT(DISTINCT pa.id)::float / COUNT(DISTINCT o.id) AS proof_rate
FROM orders o
LEFT JOIN proof_assets pa ON pa.user_id = o.user_id
```

## 4. 데이터베이스 스키마

### 4.1 핵심 테이블 목록

| 테이블명 | 역할 |
|---------|------|
| `users` | 가입 유저 정보 + 활성화 상태 + 플랜 정보 |
| `orders` | 결제 내역 및 플랜 구매 기록 |
| `wrong_answers` | 오답 등록 데이터 |
| `coaching_logs` | 코칭 진입 이력 (7일 사용률 집계) |
| `proof_assets` | 후기 / 전후 비교 / 인사이트 증거 자료 |
| `dm_logs` | 관리자 DM 발송 이력 |

### 4.2 주요 테이블 스키마

#### users

```sql
CREATE TABLE users (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email           TEXT UNIQUE NOT NULL,
  exam_date       DATE,                        -- 시험일 (고의도 유입 측정)
  plan_type       TEXT,                        -- "15d" | "30d" | "60d"
  plan_started_at TIMESTAMPTZ,
  activated_at    TIMESTAMPTZ,                 -- 활성화 완료 시각
  created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

#### orders

```sql
CREATE TABLE orders (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID REFERENCES users(id),
  plan_type   TEXT NOT NULL,
  amount      INTEGER NOT NULL,
  paid_at     TIMESTAMPTZ DEFAULT NOW()
);
```

#### coaching_logs

```sql
CREATE TABLE coaching_logs (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    UUID REFERENCES users(id),
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

#### proof_assets

```sql
CREATE TABLE proof_assets (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID REFERENCES users(id),
  type        TEXT NOT NULL,   -- "review" | "before_after" | "insight"
  content     TEXT,
  image_url   TEXT,
  is_public   BOOLEAN DEFAULT FALSE,  -- 랜딩 노출 여부
  created_at  TIMESTAMPTZ DEFAULT NOW()
);
```

#### dm_logs

```sql
CREATE TABLE dm_logs (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    UUID REFERENCES users(id),
  stage      INTEGER NOT NULL,  -- 1: 활성화유도 | 2: 실행유도 | 3: 후기요청
  sent_at    TIMESTAMPTZ DEFAULT NOW(),
  note       TEXT
);
```

### 4.3 proof_assets → 랜딩 자동 노출 연결

> 🔗 **연결 구조**
> `proof_assets.is_public = TRUE` 인 레코드를
> 랜딩 페이지 컴포넌트에서 Supabase 실시간 쿼리로 자동 렌더링합니다.

```typescript
// 랜딩 페이지 컴포넌트 (Next.js)
const { data: proofs } = await supabase
  .from("proof_assets")
  .select("*")
  .eq("is_public", true)
  .order("created_at", { ascending: false })
  .limit(6);

// 타입별 렌더링
// "review"       → 후기 카드
// "before_after" → 점수 전후 비교
// "insight"      → 인사이트 배지
```

## 7. 관리자 시스템

### 7.1 KPI 대시보드 구성

| 지표 | 기준 | 데이터 소스 |
|------|------|-----------|
| Activation (24h) | 결제 후 24h 내 온보딩 완료 | `users.activated_at` |
| 7일 사용률 | 7일 내 코칭 3회 이상 | `coaching_logs` 집계 |
| 후기 생성 수 | `proof_assets` 생성 건수 | `proof_assets` 테이블 |
| 추천 발생 수 | 레퍼럴 경로 추적 | referral 컬럼 or UTM |

### 7.2 유저 리스트 필터

관리자 페이지에서 아래 세 가지 필터를 구현합니다. 각 필터에 해당하는 유저에게 DM을 발송합니다.

| 필터 | 쿼리 조건 |
|------|----------|
| 결제 후 미활성 | `activated_at IS NULL` AND 결제 후 24h 초과 |
| 3일 미사용 | `coaching_logs` 최근 3일 기록 없음 |
| 후기 없음 | `proof_assets` 레코드 없음 |

### 7.3 DM 전략 3단계

> 📌 각 단계는 유저 상태 필터에 의해 자동 감지되며, 관리자가 수동 발송합니다.

| 단계 | 목적 | 발송 타이밍 | 대상 필터 |
|------|------|-----------|----------|
| 1차 | 활성화 유도 | 결제 후 D+1 | 결제 후 미활성 유저 |
| 2차 | 실행 유도 | D+3 미사용 시 | 3일 미사용 유저 |
| 3차 | 후기 요청 | D+7 이후 | 후기 없음 유저 |

### 7.4 증거(Proof) 시스템

> 🔄 **운영 루프**
> 데이터 → 행동 → 증거 → 전환
> `proof_assets` → 랜딩 자동 노출

| 타입 | 설명 | 랜딩 표시 방식 |
|------|------|--------------|
| `review` | 텍스트 or 캡처 후기 | 후기 카드 컴포넌트 |
| `before_after` | 점수 변화 스크린샷 | 전후 비교 배너 |
| `insight` | 유저가 발견한 패턴 | 인사이트 배지 |

## 8. 온보딩 자동화 시퀀스

### 8.1 결제 완료 트리거 흐름

```
결제 완료 (토스페이먼츠 웹훅)
  │
  ├─ orders 테이블 INSERT
  ├─ users.plan_type, plan_started_at 업데이트
  └─ 온보딩 이메일 발송 (즉시)
       ├─ 제목: "지금 바로 시작하세요 — 약점 TOP3가 준비됐어요"
       └─ CTA: 앱 바로가기 버튼

D+1 (24h 후 체크)
  │
  └─ activated_at IS NULL 이면 → DM 1차 발송 트리거

D+3 (72h 후 체크)
  │
  └─ coaching_logs 3일 없으면 → DM 2차 발송 트리거

D+7 (7일 후 체크)
  │
  └─ proof_assets 없으면 → DM 3차 발송 트리거
```

### 8.2 Supabase Edge Function 구조

```typescript
// functions/on-payment-complete.ts
import { createClient } from "@supabase/supabase-js";

export async function onPaymentComplete(payload: PaymentPayload) {
  const supabase = createClient(SUPABASE_URL, SERVICE_ROLE_KEY);

  // 1. orders 기록
  await supabase.from("orders").insert({
    user_id,
    plan_type,
    amount,
  });

  // 2. users 업데이트
  await supabase.from("users").update({
    plan_type,
    plan_started_at: new Date(),
  }).eq("id", user_id);

  // 3. 온보딩 이메일 발송
  await sendOnboardingEmail(user_email);
}
```

### 8.3 D+1/3/7 체크 Cron Job (Supabase pg_cron)

```sql
-- D+1 미활성 체크 (매일 실행)
SELECT cron.schedule(
  'check-unactivated',
  '0 9 * * *',  -- 매일 오전 9시
  $$
    INSERT INTO dm_queue (user_id, stage)
    SELECT id, 1
    FROM users
    WHERE activated_at IS NULL
      AND plan_started_at < NOW() - INTERVAL '24 hours'
      AND id NOT IN (SELECT user_id FROM dm_logs WHERE stage = 1)
  $$
);
```

## 9. 보완 과제 및 우선순위

| 순위 | 항목 | 내용 | 비고 |
|------|------|------|------|
| **P0** | 온보딩 트리거 자동화 | 결제 직후 이메일 + D+1/3/7 체크 자동화 | 활성화율 직결 |
| **P1** | proof_assets 랜딩 연결 | Supabase 테이블 → 랜딩 컴포넌트 실시간 렌더링 | 전환율 직결 |
| **P2** | 관리자 필터 대시보드 | 미활성/미사용/후기없음 필터 구현 | DM 운영 효율화 |
| **P3** | 베타 플랜 단일화 | 15일 플랜만 표시, 30/60일은 업셀 처리 | 선택 피로 제거 |
