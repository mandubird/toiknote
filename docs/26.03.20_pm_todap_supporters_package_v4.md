## 0. 핵심 방향

기존 “베타테스터”라는 표현보다  
**“토답 1기 서포터즈”**가 참여도와 자부심을 높이기에 더 적합하다.

### 왜 서포터즈가 더 좋은가
- 단순 테스트 참여자보다 **함께 만드는 사람** 느낌이 강함
- 후기/피드백 요청이 더 자연스러움
- 향후 홍보자/추천인으로 전환하기 쉬움
- “선발” 느낌이 있어서 지원율과 몰입도가 올라감

따라서 이후 문구는 **베타테스터 → 서포터즈**로 통일한다.

---

## 1. 모집 구조 추천

### 추천 인원
초기엔 **총 9명**이 가장 현실적이다.

- 시험 15일 남은 사람: 3명
- 시험 30일 남은 사람: 3명
- 시험 60일 남은 사람: 3명

### 왜 15명보다 9명이 좋은가
- 직장인이 직접 DM/관리하기에 15명은 많음
- 9명이면 각 그룹 비교 가능
- 실패/이탈이 나와도 데이터 해석 가능
- 첫 1기에서는 “많이 모집”보다 “밀도 있게 관리”가 중요

### 운영 기간
- **권장 운영 기간: 14일**
- 단, 시험 15일 남은 그룹은 7~10일만으로도 충분히 초기 검증 가능
- 30일/60일 그룹은 14일 운영이 적절

즉:
- **공통 운영 기준은 14일**
- 단기 그룹은 중간 결과도 함께 본다

## 8. 사용자 계정/플랜 세팅 방식

### 질문: 구글 회원가입하면 강제로 유료로 바꿔줘도 되나?
된다.  
Supabase/SQL 기준으로 충분히 가능하다.

### 추천 방식
서포터즈는 “결제” 대신  
관리자가 직접 **플랜 기간과 상태를 부여**하는 방식이 가장 현실적이다.

예:
- 15일 그룹 → 15일 플랜 수동 부여
- 30일 그룹 → 30일 플랜 수동 부여
- 60일 그룹 → 60일 플랜 수동 부여

### 권장 절차
1. 사용자가 구글 로그인으로 회원가입
2. 너가 DB에서 해당 사용자 확인
3. SQL 또는 관리자 페이지로 플랜 부여
4. 플랜 부여 후 DM 발송

### 예시 SQL 방향
(실제 테이블명은 네 프로젝트 기준으로 맞춰야 함)

```sql
update users
set
  program_status = 'active',
  program_start_date = now(),
  program_end_date = now() + interval '30 days',
  current_week = 1
where email = 'user@example.com';
```

또는 subscription 테이블이 따로 있다면:

```sql
insert into subscriptions (
  user_id,
  plan_type,
  status,
  start_at,
  end_at
)
values (
  'USER_ID',
  'supporters_30d',
  'active',
  now(),
  now() + interval '30 days'
);
```

### 문서화 권장
- 서포터즈 전용 플랜 타입을 따로 두는 것도 좋음
  - `supporters_15d`
  - `supporters_30d`
  - `supporters_60d`

## 11. UTM 추적 구조

### 결론
**bit.ly만 쓰지 말고, UTM을 기본으로 심어라.**

bit.ly는 짧게 만들기엔 좋지만  
핵심은 **UTM이 먼저**다.

### 추천 방식
1. 카페별로 UTM 붙인 링크 생성
2. 필요하면 그 링크를 bit.ly로 짧게 줄이기

즉:
- 원본 링크: UTM 포함
- 배포 링크: bit.ly 가능

### 예시
```text
https://www.todap.kr/landing?utm_source=naver_cafe&utm_medium=community&utm_campaign=supporters_1st&utm_content=dokchisa
```

카페별 예:
- `utm_content=dokchisa`
- `utm_content=specup`
- `utm_content=toeiccamp`

### 추천 이유
- 카페별 유입 비교 가능
- 어떤 카페에서 지원율/회원가입/실사용이 높은지 확인 가능
- 향후 재모집 때 효율 채널만 남길 수 있음

### GA4 vs 단순 bit.ly
- **GA4/내부 이벤트 추적 세팅**이 있으면 가장 좋음
- 지금은 이미 KPI 개발명세서도 있으니 **UTM + 내부 이벤트 저장**이 가장 이상적
- bit.ly만 쓰면 클릭 수는 보이지만, 이후 회원가입/활성화까지 연결이 약함

### 추천 실무
- UTM 붙인 링크를 먼저 만든다
- 필요하면 bit.ly로 짧게 만든다
- 랜딩 유입 시 UTM을 내부 event_logs/source/campaign에 저장한다

## 12. 14일이 충분한가?

### 내 의견
**“초기 검증용”으로는 충분하다.**
단, 무엇을 검증하느냐를 나눠야 한다.

### 14일 동안 검증 가능한 것
- 첫날 활성화
- 3일 사용 여부
- 오늘 할 일 체감
- 공부 방향 명확성
- 후기/증거 생성 가능성

### 14일로 부족한 것
- 실제 공식 토익 점수 상승 확정
- 장기 유지율
- 완전한 목표 달성 검증

### 그래서 결론
- **초기 1기 서포터즈 = 14일 검증**
- 이후 실제 점수 변화는 시험 이후 후속 설문으로 받는다

즉:
- 제품 효과 초기 검증 = 14일
- 진짜 점수 검증 = 시험 후 추가 회수

## 13. 놓치기 쉬운 것들

### 1. 첫날 가치 경험 강제
서포터즈가 로그인만 하고 끝나면 의미 없음  
→ 반드시 첫 코칭 결과까지 보게 해야 함

### 2. 후기 요청 타이밍
시험 끝난 뒤만 기다리지 말고:
- 3일 후
- 7일 후
- 시험 후
세 번 나눠 받아라

### 3. 공개 활용 동의
후기 받아놓고 마케팅에 못 쓰는 경우 많음  
→ 구글폼에서 익명 활용 동의 꼭 받아라

### 4. 그룹별 비교
15일 / 30일 / 60일 그룹을 나눠야  
어떤 상품이 실제로 더 잘 맞는지 보인다

### 5. 점수만 보지 말 것
초기엔 “점수 상승”보다
- 방향 명확성
- 행동 실행률
- 가치 체감
이 더 중요하다

- 추천인 혜택 연결
